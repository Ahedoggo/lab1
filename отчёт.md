## 2. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему именно он |
| --- | --- | --- |
| MinIO | Объектное хранилище, в котором размещаются файлы Iceberg | Предоставляет локальное подобие S3 с тем же протоколом обращения, что и в облаке; файлы не зависят от конкретного движка и остаются на месте после его остановки. |
| PostgreSQL 17 | Служебная база каталога | Каталогу требуется транзакционная база для своей служебной информации; там лежат только метаданные, а сами таблицы живут в MinIO, поэтому аналитическая нагрузка эту базу не затрагивает. |
| Lakekeeper 0.13.1 | Каталог метаданных Iceberg, доступный по REST | Открытая реализация с открытым REST-протоколом: Trino подключается к ней стандартным HTTP-коннектором, а отдельный Hive Metastore разворачивать не нужно. |
| Trino 484 | SQL-слой: генерация TPC-H, загрузка, преобразования и запросы | В одном образе уже есть коннекторы к TPC-H и Iceberg и поддержка S3; весь конвейер описывается SQL, без отдельного вычислительного кластера и сторонних утилит загрузки. |
| Streamlit 1.50.0 + Trino client | Дополнительный BI-инструмент: таблицы и графики | Интерфейс собирается на чистом Python и показывает пользователю выполняемый SQL; не нужны ни отдельная база пользователей, ни фоновые процессы. Для учебной задачи это легче, чем полноценная BI-платформа, хотя вся разметка задаётся кодом. |

### Скрипты развёртывания

Реальная полная конфигурация — [compose.yaml](compose.yaml), настройки — [config/trino](config/trino). JSON является допустимым подмножеством YAML; Docker Compose читает такой файл. MinIO и Lakekeeper закреплены digest образов. Идентификаторы остальных реально запущенных образов сохранены в `results/images.json`.

```powershell
# Хранилище, миграция БД, каталог, SQL-движок
docker compose up -d postgres minio lakekeeper trino
# Создание бакета и warehouse lab1
python scripts/setup.py
# Загрузка, ELT, бенчмарк и проверки
python scripts/run_lab.py --scale sf1 --repeats 5
# Дополнительный BI-инструмент, после замеров
docker compose up -d --build bi
# Фактически запущенные сервисы
docker compose ps
```

Стек использует отдельную сеть и собственные именованные тома. Старые остановленные контейнеры пользователя не изменялись. Сервисы доступны только на 127.0.0.1; пароли в конфигурации учебные. Heap Trino — 3 ГБ, лимит памяти одного запроса — 1 ГБ. При первом запуске возникла ошибка ABANDONED_TASK из-за расхождения часов внутри Docker; после установки `task.client.timeout=1h` запуск повторён. При загрузке также возникла ошибка Iceberg о движении времени назад; пайплайн продолжен с уже готовых таблиц. Неудачные попытки не вошли в измерения. Параметры хоста и Docker сохранены в `results/hardware.json`; замеры времени выполнены монотонным таймером Windows на клиенте.

## 3. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Использование |
| --- | --- | --- |
| customer | custkey, name, acctbal, nationkey, address, phone, comment | custkey служит ключом соединения и группировки, nationkey приводит к справочнику стран, а прочие поля выводятся в результате и участвуют в группировке. |
| orders | orderkey, custkey, orderdate | Через orderkey заказы связываются с позициями, через custkey — с клиентами, а orderdate отсекает всё, что не попало в последний квартал 1993 года. |
| lineitem | orderkey, linenumber, extendedprice, discount, returnflag | Соединение выполняется по orderkey, условие returnflag оставляет только возвращённые позиции, а extendedprice*(1-discount) превращается в выручку. Номер позиции оставлен, чтобы контролировать её уникальность. |
| nation | nationkey, name | nationkey даёт связь с клиентами, а name попадает в итоговый вывод как название страны. |


Границы дат: `orderdate >= DATE '1993-10-01' AND orderdate < DATE '1994-01-01'`. Это дата заказа, а не дата возврата. К исходной сортировке добавлен `custkey` как второй ключ для воспроизводимого порядка при равных суммах. Типы исходных денежных полей TPC-H сохранены. Агрегаты DOUBLE сверяются с допуском `rel_tol=1e-10, abs_tol=1e-6`, поскольку порядок сложения в распределённом плане может отличаться.

В `customer_dim` к клиентам добавляется название страны, а версии строк с обрезанными пробелами кладутся в отдельные колонки — исходный текст при этом сохраняется, чтобы сверка с эталоном оставалась точной. В `returned_lines` проходят только позиции нужного квартала с признаком возврата, там же проверяются границы цены и скидки и считается выручка по каждой строке. Дубликаты автоматически не удаляются: сначала отдельно подтвердили, что их нет, иначе итоговые суммы разошлись бы с эталоном. Данные TPC-H изначально корректны, поэтому искусственные дефекты в них не вносились.

Разбиение на секции не делалось: проекция на sf1 невелика, а деление по месяцам добавило бы массу мелких файлов. Silver и так сужен до одного квартала, а в Gold всего двадцать строк. При больших объёмах есть смысл отдельно измерить `month(orderdate)`, но здесь преимущество без проверки не заявляется.

## 5. Тесты производительности

Четыре схемы Bronze собраны по отдельности из одной и той же проекции `tpch.sf1`, различия только в формате файлов и кодеке. Сравнение ведётся запросом Q10 прямо по Bronze. Прогон Q10 по Gold для оценки сжатия исходного слоя не подходит: там уже лежит готовый ответ.

После загрузки результат каждого варианта сверили с эталоном и отдельно прогрели. Затем сделали по пять измеряемых прогонов на каждый вариант, перемешав схемы генератором с фиксированным seed 20261016. Основной показатель — медиана, а min/max показывают величину разброса. Время замерялось `perf_counter` на клиенте от отправки SQL до прихода последней строки, включая планирование, чтение, вычисления и сетевые издержки. Кэш ОС и MinIO не сбрасывался, так что это повторные, а не холодные чтения. Сборка BI закончилась до начала замеров, во время самих замеров приложение не работало.

Время записи — сумма по четырём CTAS, каждая выполнялась ровно один раз, и в неё входят генерация TPC-H, сериализация, сжатие и запись в S3. Порядок загрузки был фиксирован (GZIP, ZSTD, ORC/ZSTD, NONE), поэтому прогрев JVM мог сказаться на первых записях, и по одной этой метрике судить о скорости кодека нельзя.

| Формат | Сжатие Bronze | Медиана Q10, с | Min–max, с | Размер Bronze, МБ | Запись, с | Повторов |
| --- | --- | --- | --- | --- | --- | --- |
| PARQUET | GZIP | 10.2377 | 10.1731–10.2912 | 48.197 | 45.146 | 5 |
| PARQUET | ZSTD | 10.2387 | 10.2236–10.2874 | 48.108 | 47.163 | 5 |
| ORC | ZSTD | 12.2438 | 10.2285–12.3107 | 53.127 | 42.961 | 5 |
| PARQUET | NONE | 10.2613 | 10.1941–12.2775 | 139.276 | 43.132 | 5 |

Наименьший объём в этом прогоне занял **PARQUET/ZSTD** — 48.108 МБ. Самое короткое медианное время показал **PARQUET/GZIP** — 10.2377 с. Относительно Parquet/NONE вариант Parquet/ZSTD уменьшил размер в 2.90 раза. Для слоёв выбран именно Parquet/ZSTD: он даёт компактные колоночные файлы, которые читает весь стек, но это не означает, что он всегда быстрее любого другого варианта. Измерения сделаны на одной машине в пяти повторах, поэтому переносить их на другие объёмы и конфигурации нельзя.

Доказательства: [benchmark_runs.json](results/benchmark_runs.json), [benchmark.csv](results/benchmark.csv), [writes.json](results/writes.json), [журнал успешно выполненного SQL с query ID](results/queries.jsonl).

## 6. Часть 2 — осмысление и инструменты

### 6.1. Понять и объяснить

| Вопрос | Ответ |
| --- | --- |
| Зачем нужны большие данные и lakehouse, а не обычная БД/хранилище? | Когда объём аналитики перестаёт удобно влезать в одну реляционную базу, разумно разделить хранение и обработку: файлы лежат в объектном хранилище, разные движки читают их через общий каталог, а Iceberg добавляет согласованные снимки и безопасное изменение схемы. Небольшие наборы и точечные транзакции при этом проще держать в PostgreSQL. Иными словами, lakehouse выбирают под характер нагрузки, а не как заведомо лучший вариант на все случаи. |
| Пример schema evolution на Silver | В silver.evolution_demo было 3 строки. Затем добавили колонку source VARCHAR и переименовали её в data_source. Количество строк осталось прежним, а у старых записей новое поле пустое. SQL: sql/08_schema_evolution.sql; фактические до/после: results/schema_evolution.json. |
| Пример восстановления из снапшота | Зафиксировали снимок 8827974259937155893. После INSERT строк стало 4; time travel показал 3, а rollback вернул 3. Всё это делалось на отдельной Silver-таблице, основную витрину демонстрация не затрагивала. |


```sql
-- Актуальный ID перед своей демонстрацией:
SELECT snapshot_id FROM lakehouse.silver."evolution_demo$snapshots"
ORDER BY committed_at DESC LIMIT 1;
-- Фактически использованный ID этого запуска:
SELECT * FROM lakehouse.silver.evolution_demo
FOR VERSION AS OF 8827974259937155893;
ALTER TABLE lakehouse.silver.evolution_demo
EXECUTE rollback_to_snapshot(8827974259937155893);
```

Полный выполненный пример с INSERT — [sql/09_time_travel.sql](sql/09_time_travel.sql). Скрипт определяет ID до изменения данных. Откат снимка содержимого не следует считать универсальным откатом схемы; здесь откатывается INSERT после изменения схемы.

## 7. Выводы

Медальонная схема разводит сырые данные, их подготовку и готовый результат бизнес-запроса, поэтому каждый шаг можно проверить по отдельности. В Gold лежат 20 клиентов, и они совпадают с исходным TPC-H Q10. Сжатие экономит место на диске, однако компактность вовсе не гарантирует минимального времени выполнения SQL: сказываются чтение, декодирование, попадание в кэш и накладные расходы движка. В этом прогоне самый маленький объём дал PARQUET/ZSTD, а лучшую медиану — PARQUET/GZIP; сказанное верно только для sf1 и текущего окружения. Iceberg позволил поменять схему и вернуть содержимое снимка без ручного копирования файлов.
